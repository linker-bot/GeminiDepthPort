# 13900K 级平台性能评估

状态：静态评估与算术模型，**尚无 13900K 真机性能结果**。本阶段只建立评估和测试口径，不开始 Rust 实现，也不改变现有采集行为。

- 测试设计基线：`2526cc5705b9473d0579e3fff9f39d533cdbd86f`。
- 初始评估来源：`5071b2991d37fae238e4ad34a820d7daad1f72e6`。两者间本评估引用的采集档位、预览转换、健康探测及浏览器取图周期未改变。
- 官方 ROS 驱动：`c153462518ad674650bafa4464fda72c27ab797a`。
- 平台：Intel Core i9-13900K 或以上；实际 CPU SKU、内存、GPU、USB 控制器仍须逐次记录，不能把不同配置统一当成一台机器。
- 执行方案：[BENCHMARKS.md](BENCHMARKS.md)。记录模板：[RESULT_TEMPLATE.md](benchmarks/RESULT_TEMPLATE.md)。

## 1. 结论与重构边界

正式采集由官方原生 C++ 驱动/SDK 完成；Python 主要承担管理、预览和健康检查。仅替换管理语言不改变核心采集路径。同算法、同库、同队列和传输路径的 C++ → Rust 移植，不能预设有倍数提升，也可能回退。

连主机 SDK 和 ROS 驱动一起重构，能扩大缓冲区所有权、复制次数、按需处理和队列设计的空间。主要目标应是同档位下更少的 CPU 工作、更低的主机侧 P99 延迟与更稳定的数据新鲜度，而非把已稳定达到的 15/30 FPS 自动翻倍。

| 层级 | 有机会优化的内容 | 不应计入其收益的内容 |
| --- | --- | --- |
| 配置/Web/任务管理 | 子进程、Docker API 调用、常驻资源 | 相机曝光、SDK 内部已有原生计算 |
| 预览与诊断 | 提前限帧、融合转换、减少全图订阅、推送新图 | 把预览降采样当成正式采集帧率提升 |
| ROS 包装驱动 | 缓冲池、按需解码、消息构造、可选原生消费接口 | 所有 ROS 消费者无条件零复制 |
| 主机 SDK | 帧生命周期、传输缓冲、队列、两型号专用路径 | 相机 ASIC、固件和 USB 物理上限 |
| Linux USB/UVC/内核 | 有证据后单独评估传输与调度 | 用户态 SDK 重写自动替换内核路径 |
| 相机固件/ASIC | 当前不在范围内 | 把设备内处理时间当成可由 Rust 消除的时间 |

Gemini 335L 使用 MX6800，Gemini 2 使用 MX6600 进行设备内深度处理。重写主机 SDK 不等于替换设备内算法。开放源码与 SDK 扩展二进制还须区分，许可边界见 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。

## 与阶段二公开接口的关系

远端 `92c2fb3` 新增了 [公开数据接口](camera-interface-public.md) 和 [阶段二三机修改清单](geminidepthport-phase-two-checklist-public.md)，它们要求正式彩色为原生 YUYV，且标注为草案/待实施。当前评估不宣称现有代码已满足该契约。

本文件的具体数值属于 **WP0：已公开的双机 MJPG 输入、RGB8 输出原型样例**，不是阶段二实际设备/档位或运行配置。**WP1：三机 YUYV 契约工作负载**须另外建档，具体配置从受控环境输入，不在公开报告复制真实绑定、命名空间、场景或标定。

相同几何/帧率下，YUYV 彩色有效像素载荷为 `W×H×2×FPS`，RGB8 为 `W×H×3×FPS`；这类字节数差异来自接口编码改变，不是 Rust 加速。原生 YUYV 相比 USB MJPG 还可能增加总线流量。WP1 应优先核验 USB 控制器/拓扑和全组三机出流，不能用 WP0 的 93.696 MB/s 或乘 1.5 推导其结果。

正式契约要求 YUYV 时，不得把 MJPG 透传、RGB 输出或仅修改 encoding 标签当成兼容优化。下文上游压缩彩色路径仅是 WP0/调试预览的候选；若 WP1 采用它作为正式输出，则属于不兼容变更，不参与同契约收益对照。

## 2. 当前负载模型

以下是按 `inventory.json` 推导的有效载荷，不是实际 USB、DRAM 或网络带宽测量。假设 ROS 彩色为 RGB8、深度为 16 位，忽略行填充、协议、元数据及其他输出。

| 流 | 分辨率 | FPS | 字节/像素 | 字节/帧 | 十进制 MB/s |
| --- | --- | ---: | ---: | ---: | ---: |
| 头部彩色 | 1280×720 | 15 | 3 | 2,764,800 | 41.472 |
| 头部深度 | 640×480 | 15 | 2 | 614,400 | 9.216 |
| 腕部彩色 | 640×480 | 30 | 3 | 921,600 | 27.648 |
| 腕部深度 | 640×400 | 30 | 2 | 512,000 | 15.360 |
| 合计 | 四路 | 90 条消息/s | — | — | **93.696** |

合计约 89.355 MiB/s、749.568 Mb/s。彩色在 USB 上为 MJPG，其压缩大小随场景变化，不能用上表替代 USB 流量。单机 UDP loopback 的该载荷也不能直接套用到物理网卡速率。

- 每增加一次全量复制，复制量约增加 93.696 MB/s，逻辑读写约增加 187.392 MB/s；缓存会影响实际 DRAM 流量。
- 假设经过四次全量复制，逻辑读写约 749.568 MB/s。这是场景推导，**不是实际复制次数或 CPU 利用率**。
- 四路每路各保留四帧，原始帧缓冲合计约 19.25 MB，不包含 SDK、ROS、解码器和临时数组。
- 13900K 规格的最大内存带宽为 89.6 GB/s，实际持续带宽取决于 DDR4/DDR5、通道和负载。不得据其理论峰值推算 CPU 占用。

## 3. 已确认的路径与待量测热点

### 3.1 预览限帧发生得晚

[`preview_bridge.py`](../runtime/preview_bridge.py) 在 ROS Image 进入回调之后才限制 JPEG 处理到 5 FPS。它省掉部分转换/编码，不能省掉此前的全速图像交付与消息构造。

当两台相机都**只用于预览**时，如果专用预览支路在 ROS 传输前每流选择 5 FPS，原始载荷预算会由 93.696 降至 24.064 MB/s，减少约 **74.3%**。它不是整机 CPU 减少 74.3%；算法若仍需要全速原始图像，相关载荷不能删掉。应新增专用预览支路，而不是降低正式 raw topic 的输出频率。

### 3.2 图像转换有中间分配

预览代码包含 `bytes(msg.data)`、彩色 `.copy()`、深度 `astype(float32)` 和多次数组运算。JPEG 编码、缩放、色彩转换已经使用原生 OpenCV，NumPy 也不是逐像素解释执行。

应量测每个阶段的分配、复制和耗时，再研究池化、只读视图和融合转换。仅换成 Rust 并继续调用同一编解码库，不会自动使编码内核快几倍；替换成熟 SIMD 内核还可能变慢。

### 3.3 浏览器轮询引入展示机会等待

[`web/app.js`](../web/app.js) 每 350 ms 取图。在“新图已可用、等待下一次轮询”的条件下，等待范围为 0–350 ms；相位均匀时平均约 175 ms。源图还约每 200 ms 更新，部分帧不会被取到，不能把两者简单相加当成所有帧的真实延迟。

推送交付有机会消除这一类轮询等待，但不需要先重写 SDK。Web 改善必须独立报告，不能计作腕部到算法的延迟改善。

### 3.4 周期健康检查也在消费完整图像

[`health.py`](../runtime/health.py) 每次建立订阅，等待发现 6 秒，再采样 6 秒。发现期间回调虽不统计，匹配后仍在接收图像。Docker 的 interval 从上次检查完成后计算，忽略额外启动开销时，名义活动窗口为 `12 / (30 + 12) ≈ 28.6%`。

这不是 CPU 占用比例，实际交付还取决于发现时刻、订阅者、启动开销和负载。现有“新订阅者”也可能使原本未使用的 raw/解码路径活跃，应通过开关对照测量。

应研究采集、发布和消费边界的小型状态计数，保留启动/低频完整路径验证。只监控 SDK 收帧不能证明算法收到有效数据，不能牺牲错误检测覆盖和发现时间来制造性能收益。

### 3.5 上游已有可验证的优化路径

固定版本 `ob_camera_node.cpp` 中：

- `setupImagePublisher` / `publishCompressedColorImage` 提供 MJPG 彩色 `color/image_raw/compressed` 支路；特定订阅条件下可绕开原始解码/发布。
- `decodeColorFrameToBuffer` / `onNewFrameCallback` 包含缓冲复制和 `cv_bridge::toImageMsg` 等步骤，实际触发取决于格式和订阅者。
- `StreamStatusTracker` / `fillStreamStatus` 提供流状态；仍须核对它记录的是采集还是发布/交付。

先验证这些现有能力的效果，再决定是否替换整个 SDK。直出原始 MJPG 不等价于现有头部 960 像素宽、quality=75 的重编码预览，大小与质量必须单独控制或声明为非等价对照。

### 3.6 Rust 不自动带来跨进程零复制

当前 [`fastdds.xml`](../runtime/fastdds.xml) 明确使用 UDPv4，容器采用私有 IPC。共享内存 transport、data-sharing、loaned sample 和端到端零复制并不等价。

Humble 标准 Image 包含字符串和动态数组，不能不加验证地套用要求 plain/bounded 类型的 Fast DDS 零复制方案。必须核对实际 RMW/Fast DDS 版本、类型和进程布局。跨进程指针或 Arc 不构成缓冲区协议；USB、SDK、GPU、ROS 边界仍可能需要复制。

## 4. 收益如何估算

设被优化部分占选定指标的比例为 `p`，局部加速为 `s`：

```text
剩余成本 = (1 - p) + p / s
总 CPU 工作减少 = p × (1 - 1/s)
仅在 CPU 受限时：容量上限 = 1 / 剩余成本
```

`p` 必须来自对所选指标的测量。CPU 占比不能代入后解释为端到端延迟占比；该公式不预测 P99，也不保证固定采集档位的 FPS 会提高。

| 假设可优化部分占总 CPU | 该部分快 3×后总 CPU 工作减少 | CPU 受限时容量上限 |
| ---: | ---: | ---: |
| 10% | 6.7% | 1.071× |
| 30% | 20.0% | 1.250× |
| 60% | 40.0% | 1.667× |
| 80% | 53.3% | 2.143× |

这些是演算，不是 Rust 预测或实测结果。整体容量达到 2×，即使某部分无限快，其原占比也至少须为 50%；如果局部只快 3×，原占比须达到 75%。

平均延迟示例同样只能演算：若设备/传输 20 ms、主机 5 ms，总计 25 ms；主机快 2×，总计 22.5 ms，只减少 10%。这不是两款相机的实际时延。15/30 FPS 的更新间隔约 66.7/33.3 ms，也不是每帧延迟的严格下限。

推导输入与结果见 [performance-model.json](benchmarks/performance-model.json)，它只包含静态模型，没有真机结果；修改采集配置后应重新计算，不能把该快照当作自动更新的运行时模型。

## 5. 优化优先级

| 优先级 | 工作 | 先验证的证据 | 通过条件 / 主要风险 |
| --- | --- | --- | --- |
| P0 | 建立逐帧测量、全栈资源归属和正确性基线 | 完整环境、消费者、计数、时间戳与重复运行 | 没有可信基线不进入语言重写；测量开销须单独量测 |
| P1-A | 分层诊断替代频繁全图探测 | 原始检查 on/off 对照及故障注入 | 检测覆盖与故障发现预算不能回退 |
| P1-B | 利用压缩彩色输出，提前选择预览帧，无需求时停编码 | 独立预览和 raw 消费者组合对照 | 不降正式输出 FPS；分清等价与非等价图像输出 |
| P1-C | 消除浏览器轮询等待 | JPEG ready 到浏览器显示的逐帧测量 | 只改善 Web 指标，不计入 SDK/控制链收益 |
| P2 | 定点修改驱动数据平面 | 复制/分配、转换、队列的热点和消融实验 | 缓冲池、最新帧策略、融合转换；保持尺度/标定/配对正确 |
| P3 | SDK 特定模块替换 | SDK 内部确有不可绕开的显著热点 | 保留成熟 SIMD/编解码内核；证明新所有权/队列设计有效 |
| P4 | 全 SDK 或内核/固件重写 | P1–P3 仍无法满足业务 SLO，协议/源码/授权可用 | 高兼容性和长期维护成本；不把语言作为性能证据 |

P1-A/B 优先按主机 CPU 与资源目标安排；P1-C 是 Web 可用性方向。机器人主链若先出现 P99 排队问题，P2 的队列消融应提前，不为追求 UI 流畅度延后控制链问题。

## 6. 进入 SDK/Rust 重构的门槛

本阶段不设置自动开工日期。后续重构至少应具备：

1. 证明目标 SDK/驱动部分占足够多的 CPU 工作或关键路径，而不是把整个 C++ 进程视为都能优化。
2. 先用现有语言/上游接口验证新路径；相同输出、相同负载下达到测试方案的显著改善门槛。
3. 有逐帧正确性、尾延迟、错误恢复及许可依据；没有新增静默错误或未解释的掉帧。
4. SDK 内部结构确实限制了更小的定点改造，且长期维护两型号/固件适配成本可接受。

候选收益门槛为：相关全栈 CPU 工作至少减少 30%，或主机侧 P99 至少减少 20%，并满足统计与无回退条件，详见 [BENCHMARKS.md](BENCHMARKS.md#8-验收与决策门槛)。这是决定是否继续投入的目标，不是承诺。
