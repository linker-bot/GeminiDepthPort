# 13900K 平台基准测试方案

状态：**测试协议，尚未执行真机性能测试**。本次只增加文档和静态计算数据，不提供 Rust 实现，也没有新增可直接运行的性能采集器。已有单元测试、Web 容器 HTTP 冒烟测试均不等于性能基准。

关联：[性能评估](PERFORMANCE.md)、[结果模板](benchmarks/RESULT_TEMPLATE.md)、[验证状态](VALIDATION.md)。测试设计基线为 `2526cc5705b9473d0579e3fff9f39d533cdbd86f`；执行时另行记录实际基线/候选 commit、镜像 ID/digest 与配置哈希。

## 1. 问题与范围

优先回答：

1. 13900K 级平台上，SDK、ROS 包装、健康检查、预览与管理各增加多少主机 CPU、内存和帧处理时间？
2. 正式腕部到算法的 P99 延迟/最大数据年龄是否受复制、转换或排队影响？
3. 不换语言，现有上游压缩输出、诊断和数据路径调整能带来多少收益？
4. 只有上述对照完成后，是否有证据支持替换 SDK 的某一部分？

主机控制链、Web 展示链、部署就绪时间分开报告。不可把 UI 变流畅、等待检查变短或输出档位降低，算作 SDK 或机器人控制链加速。

本方案允许后续为测量增加最小采集器/埋点及测试配置；这些均为待实现项。本阶段不修改应用行为，也不开始 Rust。

## 2. 平台与配置控制

### 2.1 每个测试平台单独建档

记录 CPU 精确 SKU、BIOS/微码、P/E 核与 SMT、内存类型/容量/通道/速率、Linux 内核、Docker/Compose、ROS/RMW/Fast DDS、SDK/固件版本、USB 主控制器及拓扑。13900K、14900K 或其他更高配置不合并成同一硬件结果。

记录 CPU governor、功率限制、温度/有效频率、后台推理程序、GPU/驱动、容器 cpuset/限额和浏览器版本。实际内存带宽若没有测试结果则填未测，不用规格峰值替代。

第一轮保持真实部署默认调度。第二轮仅在发现调度相关尾延迟时做独立亲和性对照，记录具体 P/E 核拓扑与 cpuset；不能一边默认调度、一边绑定 P 核后宣称是语言收益。不在基准过程中自动修改 BIOS、功率或系统调度参数。

### 2.2 固定工作负载

分别执行并单独报告两种 profile，不混合求平均或相互充当同功能基线：

- **WP0（当前原型）**：下面已公开的双机 MJPG/RGB8 样例；现有代码和推导模型对应此 profile。
- **WP1（阶段二契约）**：按 [公开接口](camera-interface-public.md) 的三机原生 YUYV、可选毫米深度和显式命名绑定执行。配置/保护/契约能力仍待实现，未实现前标“不可执行”，不填写三机性能结果。具体实际档位、绑定和运行参数只存受控快照。

WP1 每路紧密 YUYV 有效像素载荷为 `W×H×2×FPS`；深度紧密载荷同为每像素 2 字节。实际消息 data 载荷按 `step×height×FPS` 计算，深度可能有行填充。三机配置须逐流求和，不能由 WP0 总量倍乘。另测 USB 实际流量：从 MJPG 改为 YUYV 可能增加 USB 成本，即使省掉主机解码。

契约草案纳入后，G1/G2 等价对照必须输出相同 YUYV/深度及时间、标定语义；不能拿“仅计帧”的 SDK 样例或旧 RGB 包装成本冒充三机契约基线。当前驱动需要的原生 YUYV 适配按阶段二计划单独实施，本次不改代码。


基准初始档位来自 `inventory.json`：

- 头部：彩色 1280×720@15 MJPG；深度 640×480@15 Y16。
- 腕部：彩色 640×480@30 MJPG；深度 640×400@30 Y16。
- 不开点云、IR/IMU、D2C 或其他新增处理；这些本来就关闭，不能再把关闭它们记作优化。
- 固定深度工作模式、尺度、曝光策略、场景/照明和相机安装状态。自动曝光不冻结时必须记录其变化；相同场景能减少 MJPG 大小变化。
- 固定 QoS、订阅者数量、传输配置、输出编码/尺寸/画质、录制状态和图像消费者行为。
- 同一语言比较使用等价 Release 构建、相同优化/SIMD/编解码库，不比较 Debug 与 Release。

正式采集与调试预览在当前实现中互斥；不能把两者同时运行的假想结果标为当前系统支持的基线。若未来新增并行模式，要作为独立候选组。

## 3. 测试指标与边界

### 3.1 逐帧标识与时间

建议新增的测试事件应携带 `run_id + camera_role + stream + session_id + source_sequence`。重连或序号回绕后改变 session，不能只用消息到达时间猜测对应关系。没有设备序号时，可在最早可见回调分配本地序号，并明确它不能识别设备到回调之前的全部丢失。

统一使用同一 Linux 主机的 `CLOCK_MONOTONIC` 纳秒时间记录主机阶段；本机不同进程可比较，不能把 GPU event、设备时钟、ROS realtime 与 monotonic 数字直接相减。

| 事件 | 定义 | 当前可见性 |
| --- | --- | --- |
| T0 | SDK 最早提供完整帧的主机回调入口 | 需要 SDK/驱动埋点；不代表曝光起点 |
| T1 | 必需解码/尺度转换完成 | 需要埋点 |
| T2 | ROS/原生输出发布入口 | 需要埋点 |
| T3 | 等价业务消费者回调收到该帧 | 需要固定消费者；不能用 Web 到达替代 |
| T4 | 该帧预览 JPEG 已可读取 | 需要把 JPEG 与源 frame_id 关联 |
| T5 | 浏览器完成该 JPEG 解码并记录绘制机会 | 需要浏览器埋点；不等于屏幕实际发光时刻 |

主要延迟：`L_host = T3 - T0`。另报告 `T1-T0`、`T2-T1`、`T3-T2`，用于定位转换与交付。Web 单独报告 `T4-T0`、`T5-T4`，其中图像缓存和原子覆盖可能使部分帧从未被展示，这些帧不得伪造 T5。

当前预览状态 JSON 与 JPEG 独立更新，不能假定刚读取的状态时间戳对应刚下载的 JPEG。没有逐帧关联协议前，不能从现有 API 得出准确的逐帧 Web 延迟。没有 T0 埋点时只能报告可观测子区间，不得将 ROS 消费时间减未校准设备时间当作 SDK 延迟。

若测真实采集到显示/动作的端到端时间，使用校准的外部 LED/光学或硬件触发方法，并另行说明设备与曝光时序。软件绘制机会、帧周期和实际传感器延迟不是同一个指标。

### 3.2 必报指标

| 指标 | 口径与单位 | 报告要求 |
| --- | --- | --- |
| 主机阶段延迟 | L_host 与各子区间，ms | 每相机/每流独立 P50/P95/P99/max，不能把腕部与头部混合 |
| 消费数据年龄 | 消费者当前时刻减其最新帧 T0，ms | 固定时间网格采样，含没有帧到达的时间段；需同一时钟 |
| 数据停顿 | 超过预先声明年龄预算的次数、持续时间、最长间隔 | 不能只统计已成功送达帧的延迟而隐藏长时间无帧 |
| 帧率和计数 | SDK、发布、消费边界分别记录 frames/s 与计数 | 区分设备/传输丢失、处理失败、策略丢弃、消费落后、重复/乱序 |
| CPU 工作 | 各相关 cgroup 的 usage 秒 / 测试 wall 秒 | 1.0 表示一个逻辑 CPU 持续忙；不是一个 P 核性能，也不是整机 100% |
| 每帧成本 | CPU 核秒 / 有效消费帧数；cycles/frame 为辅助 | 可变负载时必须同时报告分母、各流计数与总工作量 |
| 常驻与峰值内存 | PSS、cgroup memory.current / peak，MiB | 区分匿名、共享和文件缓存；RSS 不能简单相加，peak 不可用填 N/A |
| 调度/分配 | context switches、migrations、page faults、分配次数/字节 | 单独 profiling 运行；混合核 PMU 不支持的计数填 N/A，不填 0 |
| 字节搬运 | 各接口有效载荷 B/s、实测复制次数/字节 | 与 USB、UDP、真实 DRAM 流量分开，不从静态 memcpy 数目推断 |
| 功耗/能量 | CPU package W、J/有效帧；可选整机墙上功耗 | RAPL 不是整机/相机功耗；相同外部负载和采样方法下比较 |
| 恢复与就绪 | 拔插/启动到第一有效帧、恢复稳定、对外 healthy 的时间 | 分开报告；后者包含人为发现/采样等待，不能全归因 SDK |
| 正确性 | 编码、尺寸、尺度、内外参、配对、时间戳、图像/深度错误 | 任何静默数据错误为硬失败，不能用更低画质换同口径速度 |

每组须预先声明成本分母：正式业务消费帧、预览成功编码帧或实际展示帧；不同分母不能直接比较。不同相机/流混合的总计只有在工作负载比例一致时才有意义。

正确性校验应关联同一次真实帧的不同阶段；不同实时采集受噪声和场景变化影响，不要求逐像素完全相同。固定录制帧回放可用于验证转换等价性，但不能替代真实 USB/ASIC 性能测量。

13900K 有 P/E 混合核，逻辑 CPU 时间相同不代表完成了相同工作。有效频率、线程迁移和温度/功率状态应随结果保存；cycles/frame 跨不同 PMU/核型不直接合并。

## 4. 对照组

所有组都要写明 WP0/WP1 和接口版本，保持同一 profile 内相同相机配置、场景、输出需求与资源记录。共同保留相同管理服务和受控状态请求流量；需要去掉管理服务的实验必须另列，不混入语言比较。

| 组 | 路径/配置 | 目的 | 前置条件与状态 |
| --- | --- | --- | --- |
| G0 | 管理栈运行，相机关闭，无预览 | 记录管理/监测本底；不能机械地从所有组 CPU 中相减 | 现有服务可启动；资源采样记录待实现 |
| G1 | 官方 SDK 原生帧接收 + 等价最小原生消费者，无 ROS | 确定同输出条件的 SDK 主机基线 | 待实现测试采集器；必须真正执行所需解码、尺度处理和校验，不能只计回调 |
| G2 | 官方 ROS 驱动 + 等价最小原生消费者，周期全图健康探测关闭 | 与 G1 比较 ROS 包装/交付增量 | 待实现隔离测试部署、埋点和消费者；保留同等启动校验与故障观察 |
| G3 | 与 G2 相同，保留当前周期全图健康探测 | `G3-G2` 定位探测开销；正式链基线 | 同上，除周期探测外不改变其他条件 |
| G4-H | 仅头部调试预览，无正式服务，不请求 JPEG | 记录头部订阅/转换/编码成本 | 现有预览接口可启动；需测试代理续租和采样 |
| G4-W | 仅腕部调试预览，无正式服务，不请求 JPEG | 记录腕部订阅/转换/编码成本 | 同上 |
| G5 | 两台调试预览，无正式服务，不请求 JPEG | 看双预览并发与未观看支路开销 | 需续租测试代理；不能因为无浏览器而让容器租约自动过期 |
| G6 | 与 G5 相同，由受控客户端每 350 ms 请求一个角色的两路 JPEG | `G6-G5` 定位文件/HTTP 交付开销 | 待实现请求驱动；固定角色，换角色另测；不是实际浏览器绘制测试 |
| V0 | 真实浏览器查看当前预览，单独测 T4→T5 | Web 展示基线 | 待实现逐帧关联和浏览器计时；不要与 G 组的代理重复轮询状态 |
| A1 | G3 用分层诊断替代周期全图探测 | 定位诊断架构收益 | 候选实现，当前未提供；必须做故障发现覆盖对照 |
| A2 | G4/G5 的专用预览支路提前限帧，或压缩彩色直出 | 定位预览数据路径收益 | 候选实现；压缩直出存在画质/尺寸差异时标非等价，不参与同输出收益门槛 |
| A3 | V0 使用推送交付 | 定位轮询等待收益 | 候选实现；SDK/算法链保持不变，收益只归 Web |
| A4 | G3 定点减少复制/分配/队列，不换语言 | 验证驱动/SDK 新数据平面设计 | 候选实现和埋点，先小范围消融再考虑 SDK 替换 |

G1 与 G2 的差异包含封装/传输等多个层级，只能作为诊断增量，不能当作语言速度对照。只有 SDK 收帧的官方样例也不自动等价于输出 RGB/深度的 G1。

当前 `deploy.sh up` 和 readiness 流程依赖健康状态；不能直接关闭 healthcheck 后继续调用它并声称完成 G2。G2/G3 需要单独实验部署/就绪门槛，不能改坏正式配置。`docker compose down`/拔插等故障操作仅在明确的测试窗口执行。

预览代理应在 G4–G6 以同一固定周期（例如 2.5 秒）调用状态接口续租，并记录请求数量；只有 G6 增加 JPEG GET。V0 使用真实浏览器自己的状态轮询，不再叠加代理，防止双倍管理请求污染比较。每组相机实际开启/关闭由进程和序号确认，不只看界面按钮。

### 4.1 负载分层

- **L0**：主机空闲，无额外推理/录像，只保留组内指定消费者。
- **L1**：真实生产模型/应用负载，固定模型版本、精度、输入频率、并发、CPU/GPU 资源与数据源。应用自身输入语义不变。
- **L2**：有隔离范围的受控资源压力，用于验证尾延迟与恢复。明确 cpuset/内存流量或压力生成器参数；不使用无法复现的“整机大约 80%”。

先完成关键正式组 G1/G2/G3 的 L0、L1 与预览组的 L0。L2、更多档位及其他 CPU SKU 按已发现的瓶颈追加，避免先跑庞大但无法归因的笛卡尔积。

## 5. 执行流程与统计

1. **预注册**：填环境、两款固件、配置哈希、镜像、消费者、负载、采样和 SLO。没有业务绝对延迟/恢复预算时标“待确认”，不得临时以测得的值充当目标。
2. **检查正确性**：分别单台再双台，确认尺寸/编码/尺度/标定、帧身份、时间映射和观察边界。先完成一次故障检测测试。
3. **试运行**：可用 5 分钟样本筛查明显错误与瓶颈，但不据此发布最终性能收益。
4. **稳定预热**：至少 2 分钟，并等待温度、频率、内存和流状态稳定；未稳定则延长并记录。启动和冷缓存实验另列，不混入稳态。
5. **正式运行**：每组每负载至少 30 分钟，至少 3 次独立重复；交错或随机排列 baseline/candidate，控制热漂移。每次重置测试会话，保留实际次序。
6. **采样**：资源通常每秒采一次；逐帧事件写入预分配/批量日志，避免逐帧同步磁盘打印。年龄监测可用固定 10 ms 网格，并记录其开销和分辨率。
7. **结果**：逐次报告样本数、计数和分位数；P99 不只报一个跨运行混合值。按时间窗（例如 1 秒）分块分析以保留相关性；若相关性更长则增大块。P99.9 样本不足时仅作探索，不宣称严格保证。
8. **确认**：若改善与运行波动/置信区间重叠，标为不确定并增加重复（建议至少 5 次），不挑最好的一次。通过候选再做至少 8 小时目标负载稳定性测试及恢复测试。

CPU 消融/硬件性能计数可能扰动延迟。将低开销正式测量和深度 profiling 分开，做“埋点关闭/开启”控制实验；初始允许观察者开销预算为 CPU 工作 ≤2%、P99 相对变化 ≤5%。这是测量质量门槛，未通过则改采样/埋点或报告不确定，不能直接从结果扣一个常数。

低流量年龄序列也有量化误差；不足以分辨某个改善时提高计时/观察分辨率并重新检查开销。不能依靠本方案的 10 ms 网格宣称亚毫秒停顿改善。

## 6. Linux 侧工具与采样示例

以下是环境/资源诊断片段，不是完整基准程序。工具不存在、权限不足或计数不支持时记录 N/A；不要为测试自动修改全机安全策略。

```bash
uname -a
lscpu
lsusb -t
docker version
docker compose version
# 从仓库目录记录配置哈希与展开后的部署配置；内容可能含本机信息，只存本地。
sha256sum inventory.json
./deploy.sh status
```

`docker stats --no-stream` 可观察容器瞬时状态，但不能代替整个窗口的 CPU 核秒和 P99。完整归属至少包括相机、Web、预览、短命 healthcheck、原生消费者与 dockerd；浏览器在另一台机器时单独记录其 CPU，不能计作机器人主机节省。

cgroup v2 主机可以用下列方式定位一个现有容器的累计 CPU 时间。`CID` 必须替换为当前测试记录中的容器 ID；相机重启后 PID/cgroup 会改变，需要重新定位并切分计数窗口。

```bash
CID=实际容器ID
PID=$(docker inspect --format '{{.State.Pid}}' "$CID")
CGROUP=$(awk -F: '$1 == "0" {print $3}' "/proc/$PID/cgroup")
cat "/sys/fs/cgroup${CGROUP}/cpu.stat"
cat "/sys/fs/cgroup${CGROUP}/memory.current"
```

主机端读取，不在管理容器的私有 cgroup namespace 内推断宿主机路径。两个时刻的 `usage_usec` 差除以 1,000,000 得到 CPU 秒，再除以 wall 秒。cgroup 可捕获该容器内的健康检查等进程；单看容器 init PID 的资源不够。共享内存会由 cgroup 按内核规则归属，不能重复合计 PSS 与 memory.current。

可选工具包括 `pidstat`、`perf stat/record`、PSS 采样和 RAPL 能量计数。先查支持的事件与权限，再做独立 profiling；13900K 的混合核 PMU 计数不可假定能无条件合并。RAPL 需要处理计数回绕，并与单独墙上功耗区分；闲置本底不能机械扣除后宣称为相机功耗。

所有原始结果存 `work/benchmarks/<run_id>/`（已被 Git 忽略），至少包含环境、配置快照、逐帧事件、资源序列、组别/负载、计数、日志和汇总。不要向公开仓库提交真实序列号、场景画面、私有标定或本机路径。

## 7. 故障与恢复

遵守提供方独占设备和录制保护：G1 仅在正式驱动与调试驱动都停止时单独运行 SDK，其他观察者通过数据接口，不重复打开设备。不得在真实录制期间进行重启、拔插或配置扰动；阶段二保护尚未实现时只在隔离测试窗口执行，不能把当前原型声称为已有完整录制保护。

单独运行，不并入稳态延迟分布：

- 每款相机至少 10 次断开/重新连接循环，记录起止定义、第一有效帧和恢复稳定时间。
- 两台同时重连、仅重启一个容器、启动时缺一台、错误序列号/档位、消费者故意落后、负载突增。
- 用控制测试验证冻结时间戳、错误尺寸、无帧、处理失败的检测；可注入场景需隔离且标明是否真实 USB 故障。
- 分层诊断优化前后使用相同故障集合、发现时间预算和恢复策略；丢失检测覆盖直接判失败。
- 重连恢复需在预先声明稳定窗口（初始建议 2 秒）内持续正确出帧，而不只是偶然收到一帧。将额外确认窗口的时间与 SDK 恢复时间分别报告。

## 8. 验收与决策门槛

以下是首轮工程目标，不是已经实现的性能承诺；业务绝对 SLO 仍需执行前确认。

### 8.1 硬性门槛

- 相同 profile、接口版本、功能/档位、质量和消费者，无静默错误，尺度/标定/配对与时间语义不回退。WP1 原生 YUYV 排列、偶数宽度、紧密步长、载荷长度及深度毫米语义必须通过契约校验；不能只检查配置声明。
- L0/L1 正式全速最小消费者组，每流实际有效帧率目标至少为请求的 99%，并报告所有丢失原因。设备本身达不到该档位时应先修正基线/档位，不能据此归因语言。
- 有意选择最新帧/5 FPS 预览的组，单独报告策略丢弃和原始采集计数；不能用预览 5 FPS 验收代替正式 15/30 FPS。
- 不隐藏断流：必须同时通过延迟、年龄/停顿和错误计数。成功送达帧的漂亮 P99 不能抵消缺帧。
- 超过生产绝对 SLO、出现数据错误或检测覆盖丢失时，其他平均值再好也不能通过。

### 8.2 值得继续投入 SDK/数据平面重构的收益门槛

候选与其等价基线相比，满足以下至少一个主要目标：

1. **相关全栈 CPU 工作减少 ≥30%**，保持有效输出量、质量和消费者需求；同时主机 P99 不出现超过 5% 的未解释回退。
2. **正式主机 L_host 的 P99 减少 ≥20%**，尤其单独检查腕部；同时相关全栈 CPU 工作不出现超过 5% 的未解释回退。

两种目标均要求改善超过测量分辨率和运行波动，年龄/停顿、内存、恢复与正确性不回退。若某个 5% 差异落在统计噪声中，先标不确定并补测，不强行判好坏。业务最小有意义绝对改善量也应在执行前填写（例如某应用采用 1 ms）；它不是当前系统已有的时延承诺。

这些门槛首先用于现有语言/上游接口的新路径实验，不表示通过后自动开始 Rust。只有 SDK 的不可绕开结构确实挡住目标、定点修改不够且维护/许可边界清晰时，才讨论更大范围替换。

### 8.3 不等价实验

改变分辨率、帧率、曝光、画质、输出类型、健康检查覆盖或后台模型的结果可以用来做容量规划，但必须单列为非等价，不用于上述同工作量重构收益。

## 9. 提交结果的最小内容

使用 [RESULT_TEMPLATE.md](benchmarks/RESULT_TEMPLATE.md)。每次结果必须包含：

- 基线/候选 commit、镜像、配置哈希、环境及时间同步方法。
- 组别、负载、等价性声明、观察者开销与未实现的测量边界。
- 三次以上逐次指标、样本数、完整计数、P99 与最大年龄/停顿、CPU/内存/能量。
- 改善公式、噪声/不确定性、失败案例，以及“通过/不通过/不确定”。
- 原始数据本地位置；公开报告只能使用不含隐私/设备敏感信息的汇总。

未测填“未测”，不可填 0；未实现的组不写成已运行。CI 结果单列，不替代任何真机数据。
