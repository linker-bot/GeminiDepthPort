# Rust 迁移路线

当前提交初始化已有 Python/Web/Compose 原型，不引入没有实现的 Cargo workspace，也不把 SDK 的 C/C++ 采集称为 Rust 原生采集。

## 当前前置阶段：测量与定点验证，不写 Rust

先执行 [性能评估](PERFORMANCE.md) 与 [基准测试方案](BENCHMARKS.md)。目标平台为 13900K 级或以上的 Linux 主机，主机 SDK/驱动、健康检查、预览和 Web 展示分别对照。当前没有真机收益结论；理论模型和候选验收目标不能当成已实现性能。

在相同输出、计数与正确性条件下，先用现有语言/上游接口验证新路径。只有证明 SDK/驱动的可消除成本足够显著、达到预注册收益门槛且无尾延迟/错误恢复回退，再决定是否进入下列候选阶段。阶段顺序不是自动开工承诺。

本页阶段编号仅指长期 Rust 候选路线；不等同于 [三机原生 YUYV 阶段二计划](geminidepthport-phase-two-checklist-public.md)。性能对照将当前双机原型 WP0 与待实现的三机契约 WP1 分开，不把功能兼容改造自动解释为 Rust 重写。

## 阶段一：固定当前行为

- 在目标 Linux 主机验证头部 Gemini 335L 和腕部 Gemini 2 的 USB、固件及可用档位。
- 验证配置绑定、预览/正式采集互斥、双机出帧和断开恢复。
- 固定配置格式、生命周期状态和健康检查语义，增加实际设备的集成测试记录。
- 核对 SDK/扩展许可并固定可重建镜像的来源。

## 阶段二：Rust 管理服务

以现有 API、配置及测试为行为基线，迁移设备发现、配置验证、Web API、任务管理、操作锁和日志。保留 head/wrist 角色、序列号绑定及失败语义；不需要同时更换 Web 前端和底层采集协议。

## 阶段三：Rust SDK 适配

先考虑官方 C ABI 的 FFI、安全生命周期封装及 RAII，而不是直接重新实现 USB、固件及私有扩展。把采集后端抽象为独立接口，使管理层测试无需设备。

必须明确线程安全、回调所有权、帧缓冲区生命周期、断开重连和时间戳语义。受限二进制不属于可任意翻译的开源源码。

## 阶段四：可选 ROS 2 适配

将 ROS 2 发布作为可选适配层。核心采集/配置服务可以独立部署，机器人侧按需发布 Image、CameraInfo、TF 等。迁移前后用同一组数据和真机测试比较延迟、吞吐、内存及恢复行为。

## 暂不承诺

跨型号硬件同步、纯 Rust SDK 替代、所有 Orbbec 型号支持和生产级高可用均未实现。新增能力应有对应设备测试和许可依据。
